# AgentNotes AI

> Agentic AI-Powered RAG Meeting Notes Platform

Paste a raw meeting transcript and get back a structured AI summary. Ask natural-language questions about your meeting history using a RAG chatbot. Do all of this from a web app **or** directly from **WhatsApp** via an autonomous AI agent.

---

## The 30-second pitch

A meeting-notes SaaS where you paste a raw transcript and get back a structured summary (objectives, decisions, action items, next steps, etc.) generated by an LLM. On top of that sits a **RAG chatbot**: ask *"what did we decide about pricing in the meeting with Sarah on the 19th?"* and it searches your own meeting history by semantic similarity, then answers using only what was actually said — no hallucinated facts.

The same two capabilities (summarize, ask) are also exposed through an **autonomous AI agent running inside WhatsApp**, so a user can create and query meeting notes entirely by chatting, without opening the web app.

## Tech stack

| Layer | Choice | Why |
|---|---|---|
| Backend | Spring Boot 3.5 / Java 25 | Mature security (Spring Security + JWT), strong typing for business rules (plan tiers, credits, quotas) |
| Frontend | Angular 18 (standalone components, signals) | Reactive state without NgRx boilerplate; signals give fine-grained UI updates for the chat panel |
| LLM provider | OpenRouter | One API key routes to 400+ models; fail-over between models without code changes |
| Auth | JWT (stateless) | No server-side session store; token carries plan tier as a claim so auth checks don't hit the DB |
| Meeting storage | Flat JSON files | Zero infrastructure — see [Storage design](#storage-design) |
| Vector storage | Flat JSON + in-memory cosine similarity | At one user's scale (tens to low thousands of vectors), a vector DB is unnecessary overhead |
| Payments | Stripe Checkout + webhooks | Webhook-driven so subscription state updates even if the user closes the tab before redirect |
| WhatsApp agent | OpenClaw (self-hosted agent gateway) | Runs a real LLM-driven conversational agent against WhatsApp, calling this API as tools |

## System architecture

```
Angular SPA ──────────────────┐
                              ▼
WhatsApp via OpenClaw ───────► Spring Boot REST API ──► MySQL (users, plans, credits)
                                                    ──► Local JSON files (meetings, embeddings)
                                                    ──► OpenRouter (completions + embeddings)
                                                    ──► Stripe (checkout + webhooks)
```

Both client surfaces authenticate identically and hit the same endpoints — the WhatsApp agent is not a separate backend, it is a scripted client of this API. That is exactly why the RAG chatbot works identically on both without extra code.

## Auth & security model

- **Registration/login** issue a JWT signed with HMAC-SHA, containing the user's email as subject plus `planTier` and `subscriptionStatus` as custom claims — plan checks work from the token alone in most paths.
- **JwtAuthenticationFilter** runs once per request, validates signature + expiry, and populates the Spring Security context. Bad/expired tokens fail closed.
- **Two-layer Pro gate for WhatsApp**: the agent won't proceed past login if the user isn't Pro (behavioral layer), and the API independently re-checks `planTier == PRO && subscriptionStatus == ACTIVE` when it sees an `X-Agent-Channel: whatsapp` header — a free user can't bypass the gate by scripting the API directly.
- **Free-tier abuse resistance**: summary-credit decrements use an atomic conditional SQL `UPDATE ... WHERE summaryCredits > 0` rather than a read-then-write, so two concurrent requests can't both spend the last credit.

## Meeting summarization pipeline

```
POST /api/meetings
  → quota/credit check
  → OpenRouter chat completion (JSON mode)
  → parse 7 fields
  → persist + index for RAG
  → 201 response
```

**7 structured fields extracted per transcript (one LLM call):**

| Field | Description |
|---|---|
| `summary` | 2–4 sentence prose overview |
| `objectives` | Meeting goals |
| `keyPoints` | Main discussion points |
| `decisions` | Decisions made |
| `outcomes` | Results achieved |
| `actionItems` | Assigned tasks |
| `nextSteps` / `pendingDiscussions` | Follow-ups |

The prompt forces `response_format: json_object` and instructs the model to always return every field as an array (empty, never null). A second defensive layer (`extractJsonObject`) strips anything before the first `{` and after the last `}`, because models occasionally add a stray sentence around the JSON even when told not to.

## Storage design

**Users, plans, and billing** live in MySQL (relational integrity matters: foreign keys, atomic credit updates).

**Meetings and their vectors** deliberately don't:

| File | Contents |
|---|---|
| `meetings.json` | One array, one record per meeting, keyed by UUID, filtered by `userEmail` on every read |
| `meetings.md` | Same data as a human-readable Markdown log (append-only) |
| `embeddings.json` | One row per meeting: `{meetingId, userEmail, embedding[1536]}` |

All file I/O is `synchronized` at the method level so concurrent requests can't corrupt the file with interleaved writes. The whole meeting corpus can be inspected, backed up, or migrated by copying two files.

## RAG chatbot

### Indexing (once, right after a meeting is saved)

```
meeting saved
  → build index text (title + date + summary + all 7 fields)
  → OpenRouter /embeddings
  → 1536-dim vector
  → upsert into embeddings.json
```

The retrieval unit is **one whole meeting** (its summary + structured fields). Meeting summaries are already short (a few hundred tokens), so one embedding per meeting is enough — chunking only pays off when documents are too long for one embedding to represent well.

### Answering a question

```
POST /api/chat {question}
  → embed the question
  → cosine similarity vs. every meeting vector for this user
  → rank + take top 5
  → build context block
  → OpenRouter chat completion
  → answer + cited sources
```

| Parameter | Value | Why |
|---|---|---|
| Embedding model | `openai/text-embedding-3-small` | 1536 dims, ~$0.00000002/token — effectively free at this scale |
| TOP_K | 5 | Enough context without diluting the prompt |
| MIN_SIMILARITY | 0.15 | Cosine-similarity floor; below it, a meeting is treated as irrelevant |
| Fallback | Most recent 5 meetings | A vague question still gets a useful answer if nothing clears the bar |
| Answer temperature | 0.2 | Low — factual retrieval-grounded answers |

**Anti-hallucination:** The system prompt explicitly instructs: *"Answer ONLY using the meeting context provided below — never invent details that are not in it. If the context does not contain the answer, say so plainly instead of guessing."*

### Lazy backfill

Meetings created before this feature existed have no embedding. Rather than a migration script, `ensureIndexed()` checks for a missing vector on every chat request and embeds any unindexed meeting on the spot before searching — self-healing with no separate migration step.

## Autonomous WhatsApp agent (OpenClaw)

A separate LLM-driven agent process (OpenClaw, self-hosted) sits in front of WhatsApp, holds a conversation with the user, and decides for itself when and how to call this project's REST API. The agent's reasoning is driven by an LLM following a natural-language playbook (`AGENTS.md`), calling shell scripts as tools when it decides an action is needed.

### Conversational state machine

```
GREET → ASK_EMAIL → ASK_PASSWORD → LOGGED_IN
```

From `LOGGED_IN`, it branches on the incoming message:
- Message starts with `ask` → RAG question, routed to `/api/chat` — **available to all users**
- Anything else → treated as a new meeting transcript — **Pro-gated**

### Tool scripts

| Script | API call | Purpose |
|---|---|---|
| `agent-login` | `POST /api/auth/login` | Exchange email + password for a JWT |
| `agent-create-meeting` | `POST /api/meetings` | Submit a transcript, get back the structured summary |
| `agent-ask` | `POST /api/chat` | Ask a RAG question, get back the answer + sources |

Every script prints the raw response body, then `HTTP_STATUS:<code>`, which the agent reads to decide what to say next — error-handling is driven entirely by real API responses, not guessed from the LLM's judgment.

### Why this counts as "agentic"

The WhatsApp-facing LLM is given tools and a goal, and decides for itself, turn by turn, whether to ask a clarifying question, call a tool, or hand a final answer to the user. The control flow is not hard-coded if/else — it's inferred by the agent from `AGENTS.md` plus the conversation so far. This is the same tool-calling agent pattern used in production AI assistants, applied to a real, gated, multi-step business workflow.

## Reliability & failure handling

- **Model fallback chains** — every OpenRouter call sends a primary model plus up to 2 fallbacks; OpenRouter tries each in order until one succeeds. (Capped at 3 total — OpenRouter rejects a longer list with a 400.)
- **HTTP-200-with-error-payload handling** — OpenRouter sometimes returns a 200 status with an `{"error": ...}` JSON body; the client checks for this explicitly rather than trusting the status code alone.
- **Credit refund on failure** — if a paid summary credit was consumed but generation then fails, the credit is automatically refunded.
- **Structured error responses** — a `@RestControllerAdvice` global exception handler turns Spring's default detail-free 400 into a message that actually names what was wrong, so both the Angular UI and the WhatsApp agent can react correctly.
- **Explicit timeouts** — 120-second timeout on LLM calls (transcripts can be long), 10-second connect timeout.

## Monetization model

| Tier | Limit | Price |
|---|---|---|
| Free | 3 summaries, lifetime | $0 |
| Pay-per-summary credit | 1 summary per credit | $1 / credit |
| Pro subscription | Unlimited summaries + WhatsApp access | $49 / month |

Access-priority logic on every request: active Pro → unlimited; else spend a credit if available (atomic, race-safe); else check the free lifetime cap; else 403.

Stripe Checkout handles payment. A webhook endpoint (HMAC-signature verified) updates the user's plan/credits when a payment completes, so state stays correct even if the user closes the tab before the redirect.

## Running locally

### Prerequisites

- **JDK 25** (or 21+)
- **Maven** on your `PATH`
- **MySQL 8** (for the `dev` profile)
- **Node.js 20+** + Angular CLI

### Environment variables

| Variable | Purpose |
|---|---|
| `OPENROUTER_API_KEY` | OpenRouter API key (required) |
| `STRIPE_SECRET_KEY` | Stripe secret key |
| `STRIPE_WEBHOOK_SECRET` | `whsec_...` printed by `stripe listen` |
| `JWT_SECRET` | Base64-encoded JWT signing secret (prod) |

### Start order

```powershell
# 1. Start MySQL

# 2. Start backend (dev profile)
cd backend
$env:OPENROUTER_API_KEY = "your-key"
$env:STRIPE_SECRET_KEY  = "sk_test_..."
mvn spring-boot:run "-Dspring-boot.run.profiles=dev"

# 3. Start Stripe listener (note the whsec_... it prints, paste into application-dev.properties if changed)
stripe listen --forward-to localhost:8080/api/webhooks/stripe

# 4. Start frontend
cd frontend
npm install
ng serve
```

Open **http://localhost:4200**.
